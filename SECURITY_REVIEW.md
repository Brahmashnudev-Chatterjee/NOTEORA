# Phase B authentication security review

Baseline: 2026-11-12. Updated 2026-11-13 after Phase C verification. Scope: account/session authentication and authorization only. This is an implementation review with executed tests, not a penetration-test certification or production-readiness approval.

## Implemented controls

- Marketplace verification uses 256-bit random tokens, SHA-256 persistence, 24-hour expiry, active-account checks and atomic consume-and-clear. Resend replaces the prior token. Registration, self-profile and administrator user writes cannot set email verification true. Existing historical verification flags are preserved, not retroactively certified.
- Recovery uses independent random tokens, hashed persistence, one-hour expiry and atomic consumption. Reset/change increments securityVersion and revokes sessions; concurrent reset attempts cannot both succeed. Invalid/unknown recovery requests return the same response; delivery failure is recorded without token or address details. Response timing is not guaranteed indistinguishable.
- bcrypt cost 12 remains; new passwords require at least eight characters and at most 72 UTF-8 bytes to prevent silent bcrypt truncation. Existing password hashes remain usable.
- Marketplace access JWTs expire after 15 minutes, require HS256 and explicit issuer/audience, and bind a MongoDB AuthSession. Every request rechecks current account active/suspended state, role, session expiry/revocation and securityVersion. Legacy stateless tokens and cookie access authentication are deliberately invalidated: existing users must sign in once after rollout.
- Marketplace refresh credentials are opaque random secrets, stored only as hashes. Atomic rotation retains hashes of consumed credentials; reuse revokes the whole affected session. Sessions expire absolutely after seven days. User-owned device listing/revoke, current logout and all-session logout are available. A concurrent duplicate refresh intentionally revokes the family; the client serializes refresh within and across same-origin tabs using Web Locks where available.
- Refresh cookies are HttpOnly, SameSite=Strict, scoped to `/api/v1/auth`, and Secure in production. Login/register/refresh/logout require exact trusted Origin and `X-Noteora-CSRF: 1`. Ordinary account actions use bearer credentials and accept no cookie-auth fallback. The custom header plus origin checks and restrictive CORS prevent cross-site form credential use; the header is not claimed to be a secret token.
- Browser access tokens moved from localStorage to sessionStorage; old localStorage credentials are removed. Refresh credentials are never readable by JavaScript or returned as JSON. Access JWTs are intentionally returned to the authenticated client. sessionStorage access tokens remain exposed to same-origin XSS: CSP, content sanitization and broader frontend security review remain important.
- Administrator routes use current database roles. Only SUPER_ADMIN may create/promote/manage privileged accounts, and self role changes are rejected. Admin create replies expose an allowlisted public user rather than a password hash. Manual email-verification controls were removed.
- Merchant sessions use 15-minute access JWTs and separate gateway issuer/audiences/signing secret. PostgreSQL authVersion/authFamily/authExpiresAt implement refresh rotation, replay-family invalidation, expiry and logout. One active login family per merchant user is supported; a new login revokes the previous login. Current database user role/status and merchant status are checked on protected access; suspension/rejection clears merchant session families. Pending merchants retain onboarding access but cannot create payment keys until approved.
- Gateway administrator identities come from live marketplace session introspection and current ADMIN/SUPER_ADMIN roles. Merchant JWTs, refresh JWTs and the former NOTEORA_ADMIN_TOKEN are not administrator credentials. No shared administrator secret is placed in browser code. Introspection failures deny access. MARKETPLACE_AUTH_URL is operator-controlled and must be trusted; use TLS or a protected internal service network.
- Auth limits cover registration/login/recovery/resend/session activity. Forwarded IP trust defaults to zero and must be explicitly configured to known proxy hops. Limits currently use per-process memory and IP buckets; distributed deployment needs a shared limiter/store and monitoring.
- Security activity stores action/user/session identifiers and request IP, not passwords, raw reset/verification/refresh tokens or request bodies. Error responses/logging omit internal exception contents and startup connection credentials. SMTP logging/debugging are disabled. Auth responses use no-store; gateway registration errors return field descriptions rather than raw input.
- SMTP supports authenticated STARTTLS (or implicit TLS) and finite connection/socket timeouts. A development-only private file/test mailbox is available. Neither successful adapter submission nor SMTP server acceptance proves inbox delivery. Production rejects the development adapter. Local mailbox files must remain private (apply appropriate NTFS ACLs on Windows; POSIX modes alone do not configure Windows ACLs).

## Remaining risks and dependencies

- Gateway SQL migration and auth columns were applied/verified on fresh disposable PostgreSQL, with four persistent auth tests passed. This does not authorize production deployment or certify repeated Prisma migrate-deploy/rollback; those remain Phase E acceptance.
- Real SMTP/domain/deliverability checks, PostgreSQL auth tests, production TLS/cookie/proxy settings, distributed rate limits and trusted network introspection need deployment verification.
- Current npm audit after auth-library fixes still reports 7 server and 6 gateway package advisories, including critical test-tool dependencies and high Prisma-related dependencies. The high Prisma-related entries remain in the omit-dev install graph (server four, gateway three), so they must not all be dismissed as development-only. Nodemailer and Zod advisories were removed by scoped updates. No broad forced dependency upgrade was performed; unresolved advisories prevent an unrestricted security/readiness claim. Do not expose Vitest's development/UI servers to a network.
- MFA, breached-password screening, CAPTCHA, session/audit retention policies and gateway account recovery are not added in this phase. Marketplace recovery is complete; merchant management remains a separate lifecycle, with admin/team management slated for Phase E.
- Unverified users retain existing buyer/seller login behavior; verified status can now only be acquired using a valid verification token. Verification-gated publishing/purchasing policy is a separate product decision.
- Phase A payment-state overrides, webhook/ledger issues, file privacy/scanning/storage and financial correctness remain unresolved by design because the user limited work to Phase B. No live payment processing or production migration was enabled.

## Phase D financial integrity review - 2026-11-13

Paid benefits require hash-covered terms and matching accounted payment evidence; stale User.plan and subscription active booleans grant nothing. Upload quotas and accounting writes are atomic MongoDB replica-set transactions. Immutable snapshots, unique ledger/event/adjustment keys and conflicting-replay detection protect all-item multi-seller accounting. Seller report queries are identity-scoped; SUPER_ADMIN-only versioned policy changes require audit reasons. Manual PAID and refund-completed controls are disabled.

Signed webhook processing is isolated to sandbox/non-production and checks exact amount, currency, event sequence and environment. This is not an authorised-provider integration. No public route accepts customer/admin claims as refund confirmation. The internal accounting seam accepts only trusted integration evidence; authentic provider verification remains a future approved phase. No live credentials, payments or payouts were used.

102 backend tests and15 real Chrome regressions pass in Phase D, including isolation, concurrent quota/ledger/refund writes and denial cases. The isolated PostgreSQL checks cover existing auth/schema definitions only. No production migration occurred. Replica-set deployment, approved tax/fee policy, legacy-record reconciliation, real SMTP, dependency remediation and production operations remain blockers. Dependency counts above are prior Phase C audit evidence, not a fresh Phase D advisory scan; dependencies were not changed in this phase.
